# v9.11 — selectable CUTLASS launches for GLM53 W4A8

**Build update:** use the v9.11.1 kit and [sequential-build instructions](V9.11.1-BUILD.md).
The original v9.11 compiled all seven variants in one CUDA unit and exhausted
an 8 GiB builder. Kernel IDs and the tuning procedure below are unchanged.

This patch is stacked on v9.10 / PR #13. The v9.11 image includes BOTH patches:
Humming EP + bounded CP padding, and the separate CUTLASS tuning extension.
Only one MoE backend runs at a time. DFlash remains disabled.

## What changes

The stock dispatcher has specializations for hidden size 7168. GLM's gate/up
`N=4096,K=6144` and down `N=6144,K=2048` use the generic path; at C40 this
selects `CO 128x32x512, cluster=1`. The extension adds seven explicit choices
over the SAME SGLang mixed-input CUTLASS mainloop and epilogue. It preserves
signed INT4 packing, BF16 group-128 weight scales, checkpoint static activation
scales, actual GPU expert counts, permutation, SiLU, combine and EP reduction.

| ID | Schedule | Tile | Cluster |
|---|---|---|---|
| 0 | Original dispatcher | Original | Original |
| 1 | Cooperative | 128×16×512 | 1×1×1 |
| 2 | Cooperative | 128×32×512 | 1×1×1 |
| 3 | Cooperative | 128×64×512 | 1×1×1 |
| 4 | Pingpong | 64×16×512 | 1×1×1 |
| 5 | Pingpong | 64×32×512 | 1×1×1 |
| 6 | Cooperative | 128×32×512 | 2×1×1 |
| 7 | Cooperative | 128×16×512 | 2×1×1 |

These are CUTLASS's **transposed** tile axes: the second axis is tokens, the
first is output channels. Tile K stays 512 to preserve the existing scale
packing. The operator is restricted to SM90, 32 local experts, GLM dimensions
and input capacity at most 64×top8 rows. GPU problem sizes remain authoritative.

Without `SGLANG_GLM53_CUTLASS_CONFIG`, the stock path is used. A tuning JSON
selects gate/up and down separately for exact batch sizes 1..64. Unmeasured
batches, other model/EP geometry and large prefill batches use the stock path.
The JSON is loaded once before graph capture; change it only with a restart.
An invalid, missing or incompatible explicitly configured JSON fails startup.

The extension is compiled during image build, using the same pinned CUTLASS
commit as the source base (`57e3cfb47a2d9e0d46eb6335c3dc411498efa198`). Download
SHA256 is checked. Build needs nvcc and internet access to codeload.github.com;
no GPU is needed for compilation. BUILD.json records torch/CUDA and binary hash.
No compiler runs inside decode. The main sgl_kernel package is not replaced.

## Build once for both patches

```bash
tar -xzf glm53-hicache-v9.11.1-release.tar.gz
cd glm53-hicache-v9.11.1-release
bash build.sh --push
```

For Humming with patch 1, use `kubectl apply -f manifests/02-humming.yaml`.
This uses the existing deployment, node w06 and eight GPUs with Recreate.
For CUTLASS tuning, the same deployment temporarily runs sleep instead of the
server. Serving is interrupted during the kernel test; no extra GPUs are used.

## Short CUTLASS search on one actual checkpoint layer

On the host with kubectl, from the extracted v9.11.1 build-kit directory:

```bash
NS=inf-glm53
kubectl -n "$NS" apply -f manifests/00-kernel-check.yaml
kubectl -n "$NS" rollout status deployment/sglang-glm53-dcp4 --timeout=7200s
POD=$(kubectl -n "$NS" get pod -l app=sglang-glm53-dcp4 -o jsonpath='{.items[0].metadata.name}')
kubectl -n "$NS" exec "$POD" -c sglang -- \
  torchrun --standalone --nproc-per-node=8 \
  /opt/glm53-cp8-dcp4-v1/benchmarks/tune_glm53_cutlass.py \
  --model-path /mnt/model-pvc-w4fp8 \
  --batches 40 48 --iterations 30 \
  --output /mnt/cache/glm53-cutlass-tuning.json
```

The checkpoint layer is loaded once. Gate/up is searched first, then down;
this is not an exhaustive global optimum. Every candidate is compared with
stock using changing inputs/routes, including seven ranks with zero local
work. Stock is checked against an independent dequantized FP32 reference.
Times include local routing, quantization, both GEMMs, SiLU and combine in a
CUDA graph. The score averages the worst-rank timings for uniform and skewed
routing. A fresh confirmation must beat stock by at least 3%; otherwise the
saved pair is `[0,0]`. A kernel/correctness failure aborts without writing a new
JSON. Inspect the command exit status; an older JSON is not evidence of success.

Only after that command completes successfully:

```bash
kubectl -n "$NS" cp -c sglang \
  "$POD:/mnt/cache/glm53-cutlass-tuning.json" ./glm53-cutlass-tuning.json
python3 -c 'import json; print(json.load(open("glm53-cutlass-tuning.json"))["pairs"])'
kubectl -n "$NS" apply -f manifests/03-cutlass-tuned.yaml
kubectl -n "$NS" rollout status deployment/sglang-glm53-dcp4 --timeout=7200s
```

Then run GSM8K and the existing 60k+15k+1k serving benchmark. The tuning test
uses synthetic activations/routes and excludes attention and collectives; its
gain is a kernel candidate, not proof of full-model speed or production accuracy.
For a clean comparison with Humming, both serving manifests keep CP8/DCP4,
HiCache, FP8 KV, batch40 graph, prefill buckets and padding settings aligned.

To return to stock CUTLASS, apply `manifests/01-cutlass.yaml`; to Humming with
patch 1, apply `manifests/02-humming.yaml`. No image rebuild is needed between
these three configurations. No full-size 7168 model/checkpoint is required.

## Local validation and limits

93 host tests passed, including four new dispatch/schema/argument-preservation
tests; 28 chunk/geometry checks are inherited from patch 1. Python and shell
syntax and manifest invariants were checked. The pinned CUTLASS archive was
downloaded and its hash verified during preparation.

**Not run here:** nvcc compilation/linking, GPU correctness/capture, image build,
model startup, model eval or throughput. Docker build is the C++ compiler gate;
the torchrun test is the GPU gate. Both PRs remain drafts for that reason.
No configuration is pre-labelled faster, and no 2× serving gain is claimed.
The profile places only about 10.6 of 32.3 ms in expert GEMMs; improving them
cannot remove attention, dense GEMMs and communication time.
