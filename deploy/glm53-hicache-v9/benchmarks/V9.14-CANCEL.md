# v9.14: отмена запросов после отключения клиента

Выпуск поверх v9.13 / PR #16:
`ca6f232142316e660c2defc3b1ee2b4ddc197818`.
Переносит подготовленный `GLM53_CANCEL_V1` в обычный комплект сборки и добавляет
явное закрытие SSE и вложенных генераторов. Новые изменения runtime затрагивают
только `tokenizer_manager.py` и `serving_chat.py`.

## Исправление

При отмене `generate_request()` прежний обработчик `BaseException` удалял RID,
даже если запрос уже выполнялся в scheduler. Отложенная отмена затем не находила
состояние и не отправляла `AbortReq`. Генерация могла продолжаться после обрыва
HTTP-соединения.

- Успешный dispatch отмечается отдельно для одиночного запроса и batch.
- Ошибка до dispatch удаляет локальное состояние без отправки отмены.
- После dispatch отправляется `AbortReq`, а состояние сохраняется до обычного
  завершающего ответа или abort echo. Вывод, уже находящийся в передаче, штатно
  обрабатывается; сообщения об удалённом состоянии не подавляются.
- Повторная отмена одного состояния не дублирует отправку. Ошибка отправки
  сохраняет состояние и возможность повторной попытки, не останавливая отмену
  других участников пакета и не подменяя исходное исключение.
- При `n > 1` учитываются prefix warmup и RID всех отдельных samples.
- Закрытие внешнего генератора явно закрывает вложенные генераторы и waiter
  tasks. Поздняя очистка проверяет принадлежность состояния: повторное
  использование завершённого RID не отменяет новый запрос.
- Chat StreamingResponse закрывает подготовленный генератор в `finally`, в
  том числе при ошибке отправки HTTP-заголовков и ASGI 2.4 `ClientDisconnect`.
  Очистка защищена от повторной отмены AnyIO. Этот endpoint больше не зависит
  от двухсекундной background task. Проверка входа до HTTP 200 сохранена.

CP8/DCP4, Humming, DFlash2, графы, HiCache, sampling и аргументы launcher в этом
выпуске не меняются. Патч устраняет потерю отмены; причину достижения 900-секундного
таймаута исходным запросом и прирост производительности нужно оценивать отдельно.

## Основа образа и воспроизводимость

Dockerfile закреплён на digest проверенного работающего v9.13:

```text
i501-harbor-infra.ai.turbocloud.ru/images/lmsysorg/sglang@sha256:cbe5d638e2c95cefb49a6c5cd3c562a247fae67f731b877f5a824fa604179155
```

В сохранённой диагностике исходные SHA256 совпали с этим v9.13 checkout:

| Файл | SHA256 до исправления |
| --- | --- |
| `tokenizer_manager.py` | `bdfaa4f4f214515f2138a3a82e8215882735490dfa85c271d2c41830b682ad33` |
| `serving_chat.py` | `7b05e6ab1d09a71ce253040c9cd62ea7c55a52020b44cf9b76d91c8df9e23240` |

`make_bundle.py` требует чистые committed-исходники. `REVISION.json` содержит
commit/tree v9.14, предыдущий v9.13, digest основы и признак `GLM53_CANCEL_V1`.
Комплект содержит полный `runtime.patch`, разницу `v9.13-to-v9.14.patch`, overlay,
установщик, тесты, скрипт короткой проверки и `SHA256SUMS`.

Установщик проверяет все входные файлы до первой записи. Совпадающие SHA256
v9.10/v9.12 и закреплённого upstream также поддерживаются для кумулятивной сборки;
по умолчанию используется именно проверенный v9.13. Неизвестные изменения в
этих файлах отклоняются. Повторная установка идемпотентна.

## Сборка тем же порядком

На хосте с Docker и доступом к Harbor:

```bash
git clone --filter=blob:none \
  --branch work/glm53-cancel-v9-14 \
  https://github.com/leoong55/sglang-lasolovev.git glm53-v914-src
cd glm53-v914-src
python3 deploy/glm53-hicache-v9/make_bundle.py ../glm53-hicache-v9.14
cd ../glm53-hicache-v9.14
bash build.sh --push
```

Образ, который создаст команда:

```text
i501-harbor-infra.ai.turbocloud.ru/images/lmsysorg/sglang:glm53-hicache-v9.14-0bcd822377da
```

Это имя для сборки; наличие опубликованного Docker-образа этим документом не
утверждается. Сборка не запускает NVCC/CUTLASS, не скачивает веса, не обновляет
Torch/CUDA/Humming. CPU-тесты выполняются на установленных исходниках внутри
образа. После сборки `build.sh` повторно проверяет файлы и отмену в новом
контейнере, затем выполняет push. GPU для этих проверок не требуется.

CI также публикует архив комплекта в artifact `glm53-hicache-v9.14-<commit>`.
Этот архив содержит исходники для сборки, не слои Docker-образа.

## Замена текущей модели

Текущий сервис находится в KServe/Knative. Новый image нужно указать через тот
исходный ресурс платформы, который создаёт модель, сохранив текущие args/env,
тома и таймауты. Замена image только в дочернем Deployment может быть отменена
оператором. Поле управляющего ресурса здесь не угадывается.

Для первой проверки сохраните TP8/EP8/CP8/DCP4, Humming, DFlash block8/window2048,
max-running40, mem-fraction0.78, HiCache96 и prefill16384 — параметры из последней
диагностики. Сравнительные манифесты 05–10 для `inf-glm53` сохранены как отдельные
профили; здесь у них обновлён только image. Не применяйте их поверх текущего
InferenceService как замену его конфигурации.

Откат — вернуть прежний digest в том же управляющем ресурсе. Патч вступает в
силу после штатной замены пода и не внедряется в уже работающий Python-процесс.

## Короткая проверка отмены

С хоста с kubectl из каталога распакованного комплекта, указав новый pod:

```bash
NS=inf-a0de6091-66ad-454c-beba-6a2b098e5470
kubectl -n "$NS" get pods
POD='ИМЯ_НОВОГО_ПОДА'

kubectl -n "$NS" exec "$POD" -c kserve-container -- \
  cat /opt/glm53-cp8-dcp4-v1/REVISION.json
kubectl -n "$NS" exec "$POD" -c kserve-container -- \
  python3 /opt/glm53-cp8-dcp4-v1/install.py --verify-only
kubectl -n "$NS" exec -i "$POD" -c kserve-container -- \
  python3 - --model alpha-fm < cancel-smoke.py
kubectl -n "$NS" logs "$POD" -c kserve-container --since=2m | \
  rg 'GLM53 cancel-v1:|state was deleted in TokenizerManager'
```

Скрипт создаёт один запрос с `max_tokens=4096`, `ignore_eos=true`, читает поток
пять секунд после первого содержательного чанка, печатает RID и закрывает
соединение. Текст ответа не выводится. Код 0 означает намеренный disconnect;
серверную отмену подтверждают отдельные строки с тем же RID:

```text
GLM53 cancel-v1: dispatched scheduler abort for rid=...
GLM53 cancel-v1: terminal output for cancelled rid=...
```

Для запроса в очереди вместо второй строки допустима
`GLM53 cancel-v1: scheduler abort echo for rid=...`.
После обработки текущей итерации scheduler запрос должен исчезнуть из running
requests, активный KV вернуться к фоновому уровню. На занятом сервере общие
значения не обязаны стать нулевыми. Ошибки для того же RID и продолжающаяся
генерация в течение минут означают, что проблема остаётся.

Затем проверьте распространение disconnect через внешний маршрут с ключом,
уже заданным в `GLM53_KEY`:

```bash
python3 cancel-smoke.py --base-url https://alpha-fm.ai.turbocloud.ru --model alpha-fm
```

Ключ берётся из окружения и не печатается. Короткий тест отключения клиента
не заменяет наблюдение настоящего таймаута queue-proxy на обычной нагрузке.

## Проверки и ограничения

22 проверки отмены исполняют реальные тела методов на CPU с подставленными
tokenizer/transport. Проверены до/после dispatch, ошибки, закрытие генератора,
частичный batch, `n > 1`, повторный RID, повторная отмена и abort echo. Проверки
SSE используют настоящий Starlette 0.48.0 / AnyIO 4.10.0 для ASGI 2.3 и 2.4:
disconnect при отправке, ошибка заголовков/тела, отмена задачи, штатное завершение
и HTTP 400 до начала стрима. В Docker эти же тесты используют установленные
версии Starlette/AnyIO без их обновления. Шесть тестов установщика проверяют
идемпотентность, отказ при несовпадении SHA256 и откат при ошибке записи.

```bash
export SGLANG_SOURCE_ROOT="$PWD"
python3 -m unittest discover -s deploy/glm53-hicache-v9/tests -p 'test_host_cancel*.py' -v
python3 -m unittest discover -s deploy/glm53-hicache-v9/tests -p 'test_host_install.py' -v
```

Сборка Docker-образа, реальная отмена через Knative, освобождение DFlash KV на
H200 и влияние на скорость здесь не подтверждены. Матрица LoRA, мультимодальности,
нескольких tokenizer workers и disaggregated serving отдельно не проверялась.
Многоминутный нагрузочный прогон не нужен для первой проверки отправки отмены.
