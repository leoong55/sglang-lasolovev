# Проверка v9.7 на исходной prefill-нагрузке

База — присланный оператором тест: 300 запросов, 20 префиксов по 60k,
suffix 15k, output 1k, concurrency 40, temperature 0.3, seed 0,
один warmup. Результат сохранён в `operator-v9.6-c40-prefix20.json`.
Один warmup не означает прогрев всех двадцати префиксов.

| Показатель | Присланный результат |
| --- | ---: |
| Успешные / ошибки | 300 / 0 |
| Output throughput | 512.75 tok/s |
| Mean TPOT | 66.81 ms |
| P50 / P95 TTFT | 1422.48 / 68419.79 ms |
| P95 / P99 TPOT | 99.40 / 134.41 ms |
| Duration | 585.08 s |

Не сравнивать этот результат напрямую с short-input тестом 1k/1k или
объявлять разницу с прежними 549.67 tok/s эффектом одного патча:
одновременно снятого GPU-профиля и одинакового состояния кэша нет.

## Сравнение на одном образе

Оставить прежние CP8/DCP4, mem fraction, draft window 2048, request limit,
graph buckets и benchmark image. Для каждого режима задать две env,
перезапустить процесс и начинать первый прогон с пустым кэшем. Это операция
оператора стенда; данный патч ничего не применяет к кластеру автоматически.

| Режим | `SGLANG_GLM53_HICACHE_INDEX_ELISION` | `SGLANG_GLM53_BOUNDED_DRAFT_FASTPATH` |
| --- | --- | --- |
| A: пути v9.6 | 0 | 0 |
| B: только экономия DSA | 1 | 0 |
| C: только быстрый draft | 0 | 1 |
| D: оба изменения | 1 | 1 |

В benchmark-контейнере выполнить `bash run-prefix20.sh`; файл находится
рядом с этим документом. Имя результата задаётся через `BENCH_RESULT_NAME`,
например `BENCH_RESULT_NAME=mode-b-cold.json bash run-prefix20.sh`.
Следующий прогон без рестарта записать отдельно как `mode-b-warm.json`.
Для A/B нужны одинаковые условия и отсутствие посторонней нагрузки.

По каждому режиму сохранить полный startup log, фактический `max_total_num_tokens`,
загруженный image digest, effective argv, сообщения о capture/replay и весь
benchmark JSON. Для draft проверить рост `reused` в сообщениях
`GLM53 bounded draft windows`; для DSA — `stores 21/78 target layers`.
Отсутствие прироста reused при частых prefills не считать подтверждением
ускорения: это консервативный fallback по условиям жизненного цикла.

Больший пул может уменьшить cache churn и TTFT. Сравнивать decode при том же
размере батча и учитывать speculative acceptance именно этого прогона.
Показатель total token throughput включает cached input и не равен скорости
вычисленного prefill. Peak concurrency из клиента не равен scheduler batch.

## Корректность перед оценкой скорости

Повторить одинаковые greedy-запросы (temperature 0, одинаковый лимит вывода)
в режимах A и D: короткие задачи, длинные общие префиксы, повтор после
подтверждённого L1-вытеснения/L2-восстановления. Для проверки восстановления
недостаточно большого `cached_tokens`: нужны серверные load-back события.
Проверить отмену, retraction/readmission и повторное использование request slot.
Сравнивать фактические ответы/токены, а не только отсутствие HTTP-ошибок.
GSM8K 200 примеров / 5-shot из прежнего теста — дополнительная проверка качества,
не доказательство корректности L2. Любое расхождение нужно разобрать до вывода
об ускорении; параллельные FP-вычисления сами по себе не гарантируют побитовую
детерминированность между отдельными запусками.

В этой среде доступны CPU-тесты реальных методов со средствами имитации DMA
и компиляция имеющихся SM90 bridge kernels. GPU DMA, CUDA graph replay,
исходная модель и performance-тест здесь не исполняются.

## Что остаётся для профиля GPU

Если TPOT остаётся высоким, отделить время synchronous draft backing/accepted
filtering, indexer, FlashMLA target verify, DCP collectives и W4A8 MoE.
Этот патч не устраняет все CPU/GPU синхронизации. Новый 32-head SM90 kernel и
изменение DCP combine нельзя оценить по одной сводной строке benchmark.
