# GLM53 v9.8: isolate CP decode communication and MoE weight kernels

This is an experimental cumulative image; new fusion defaults off. GPU results
are pending. The current no-DFlash short-context reference is 1027.29 output
tok/s, mean TPOT 37.65 ms, P95 TPOT 38.26 ms at concurrency 40. The supplied
10-second profile had about 4.27 ms of non-DCP all-reduce and buffer copies per
decode step, 3.56 ms of DCP NCCL, and 11.81 ms of W4 MoE GEMMs. These are summed
kernel durations and may overlap; they are not additive predictions of savings.
This patch addresses the attention part of the non-DCP reduction, not all MoE
reductions. Reaching 2000 tok/s at C40 needs roughly 20 ms/token, so fusion alone
does not establish that target.

## Three controlled serving arms

Use the same v9.8 image, CP8/DCP4, W4AFP8, FP8 KV, HiCache policy, memory fraction,
request limit, graph buckets and prefill chunk in every arm. Remove **all**
`--speculative-*` options and `--glm53-draft-cache-window`, as in the no-DFlash
baseline. Restart between arms. Do not change mem-fraction or add graph bucket
40 during this comparison.

| Arm | Additional launcher args | What it measures |
| --- | --- | --- |
| A | `--glm53-cp-decode-fusion off` (no explicit FlashInfer backend) | Current CP path |
| B | `--glm53-cp-decode-fusion off --flashinfer-allreduce-fusion-backend trtllm` | Existing FlashInfer allreduce dispatch/workspace effects |
| C | `--glm53-cp-decode-fusion attention --flashinfer-allreduce-fusion-backend trtllm` | B plus attention all-reduce/residual/RMSNorm fusion |

For C, add these entries to container `args`:

```yaml
- --glm53-cp-decode-fusion
- attention
- --flashinfer-allreduce-fusion-backend
- trtllm
```

The launcher adds the backend if omitted in C. `off` never removes an explicit
backend; for rollback to A, set `off` **and remove the backend option**.
In C, require a startup/warmup log `GLM53 CP decode attention fusion: eligible`.
`workspace unavailable; ordinary path` means fusion was not exercised.
Record the launcher effective argv, allocated KV slots and free GPU memory.

## Kernel gate on 8 GPUs, before enabling C

Run inside the new image while the serving workload is idle. This loads no model
weights, but creates additional CUDA contexts and communication workspaces.
For a standalone validation container use the same 8 GPUs/NVLink visibility and
IPC settings as serving. Do not run concurrent benchmarks during this check.

```bash
torchrun --standalone --nproc-per-node=8 \
  /opt/glm53-cp8-dcp4-v1/tests/check_cp_fusion_gpu.py
```

It checks rows 1/2/8/32/40/48/64 in eager mode and graph replay with changed inputs.
Every rank contributes distinct data; residuals are replicated. The independent
reference uses NCCL and an explicit RMSNorm formula. FP rounding tolerance is
rtol 0.02 / atol 0.025. Falling back to an unfused path fails the check. This does
not replace full-model accuracy/long-context checks.

## Serving runs (benchmark pod)

Use the same command across all arms. Explicit temperature/seed avoid the vLLM
client's changed default. Run A/B/C and then repeat A to detect drift; retain
individual runs and compare median TPOT rather than selecting the best result.
The fixed greedy setup below creates a new controlled baseline; the older
1027.29 result did not explicitly set temperature, so it is only a reference.

```bash
export ARM=A
vllm bench serve \
  --backend openai-chat \
  --base-url http://sglang-glm53-dcp4.inf-glm53.svc:8080 \
  --endpoint /v1/chat/completions --model GLM-5.3 \
  --tokenizer PhalaCloud/GLM-5.3-W4AFP8 \
  --dataset-name random --random-input-len 1000 --random-output-len 1000 \
  --num-prompts 400 --max-concurrency 40 --request-rate inf \
  --num-warmups 1 --ignore-eos --temperature 0 --seed 0 \
  --extra-body '{"chat_template_kwargs":{"enable_thinking":true}}' \
  --percentile-metrics ttft,tpot,itl,e2el --metric-percentiles 50,95,99 \
  --save-result --save-detailed --result-dir /results \
  --result-filename "glm53-v98-${ARM}-short.json"
```

Only after a repeatable short-context gain, run the production-pattern test on
A and the winning arm, each following a fresh server restart so cache warmth is
comparable. Keep the existing HiCache ratio and 20-prefix schedule:

```bash
vllm bench serve \
  --backend openai-chat \
  --base-url http://sglang-glm53-dcp4.inf-glm53.svc:8080 \
  --endpoint /v1/chat/completions --model GLM-5.3 \
  --tokenizer PhalaCloud/GLM-5.3-W4AFP8 \
  --dataset-name prefix_repetition \
  --prefix-repetition-prefix-len 60000 --prefix-repetition-suffix-len 15000 \
  --prefix-repetition-output-len 1000 --prefix-repetition-num-prefixes 20 \
  --num-prompts 300 --num-warmups 1 --max-concurrency 40 --request-rate inf \
  --ignore-eos --temperature 0.3 --seed 0 \
  --extra-body '{"chat_template_kwargs":{"enable_thinking":true}}' \
  --percentile-metrics ttft,tpot,itl,e2el --metric-percentiles 50,95,99 \
  --save-result --save-detailed --result-dir /results \
  --result-filename "glm53-v98-${ARM}-long.json"
```

Accept only a repeatable improvement with no failed requests, no material
long-context TTFT/TPOT regression, and acceptable measured KV-pool size. Repeat
the same 200-example GSM8K check in both arms (prior reference 199/200); inspect
changed examples. Tiny reduction-rounding differences can change greedy tokens,
so exact text equality is not a universal correctness criterion. A 200-question
math score alone cannot certify long-context/cache correctness.

## Isolated FP8 question: one GPU, about one layer of weights

Run while the server is idle, or in a separate container. This uses synthetic
weights representing 32/256 experts, not the 700+ GiB FP8 checkpoint. The model
directory supplies configuration only. CUDA contexts, kernels and temporary
buffers also consume memory; the footprint exceeds the raw weight sizes.

```bash
torchrun --standalone --nproc-per-node=1 \
  /opt/glm53-cp8-dcp4-v1/benchmarks/compare_moe_kernels.py \
  --model-path /mnt/model-pvc-w4fp8 --batches 40 48 --seeds 7 19 41 \
  --iterations 100 --output /tmp/glm53-moe-kernels.json
```

All three paths receive identical weights/routes and are checked against BF16
local-expert reference outputs. Activations are quantized using each kernel's
scheme, so they need not be bit-identical. The test rejects nonfinite outputs
or relative L2 error above 0.08; timings include each path's local permutation,
activation quantization, both GEMMs, SiLU and combine. They exclude routing gate,
shared expert, TP/EP communication, attention, and scheduling. FP8 kernel failure
is a failed experiment, not evidence it is slow. No fallback result is relabeled
as another backend. Saved JSON contains individual seeds and timing samples.

If FP8 is not faster here, do not pay the full-checkpoint KV cost. If it is faster,
estimate the benefit using the measured fraction of step time first, then test
integration separately. A 2x MoE speedup cannot imply a 2x complete decode speedup.

Fetch the result from the host with kubectl:

```bash
POD=$(kubectl -n inf-glm53 get pod -l app=sglang-glm53-dcp4 \
  -o jsonpath='{.items[0].metadata.name}')
kubectl -n inf-glm53 cp -c sglang \
  "$POD:/tmp/glm53-moe-kernels.json" ./glm53-moe-kernels.json
```
