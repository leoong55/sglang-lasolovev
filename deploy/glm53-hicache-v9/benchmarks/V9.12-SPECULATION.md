# v9.12: Humming, DFlash2 и штатный EAGLE/MTP

Патч основан **непосредственно на v9.10**, коммит
`1f1171df23c98755c7d479d8befe071a9e13ecbe`. Изменения v9.11/CUTLASS tuning
в него не входят. Образ по умолчанию собирается поверх уже готового
`glm53-hicache-v9.10-0bcd822377da`. Сборка проверяет хэши исходников и наличие
Humming 0.1.12; nvcc/CUTLASS-компиляции и установки новых зависимостей нет.
Штатный CUTLASS из v9.10 остаётся доступен через `--moe-runner-backend cutlass`.

## Что изменено

1. Launcher допускает Humming + DFlash2 в существующем CP8/DCP4 профиле.
   Проверка target-токенов, sampling/greedy acceptance, порядок projection/norm/RoPE,
   FP8 KV target и BF16 KV draft сохранены.
2. В bounded draft одна операция compaction принятых строк заменяет четыре
   отдельных boolean-index операции. Для decode удалены ещё четыре boolean-index
   операции и scatter-reduce поиска конца запроса: принятый префикс блока из восьми
   строк целиком помещается в кольцо 2560, включая переход через его границу.
   Ветка длинного prefill по-прежнему отбрасывает старые обороты кольца.
3. Добавлены фактические признаки `draft_graph`, `verify_graph`, `sampler_in_graph`
   и необязательный ограниченный замер этапов DFlash.
4. Добавлен явный профиль `--glm53-profile tp8` для штатного GLM EAGLE/MTP.
   Он требует TP8/EP8/DP1/DCP1 без CP. Перед GPU-загрузкой launcher проверяет
   локальный `config.json`, группы MTP-весов слоя 78 и наличие их shard-файлов.
   `EAGLE + CP8/DCP4` отвергается: реализация DCP verification здесь рассчитана
   на DFlash, а не на EAGLE tree/draft state.

## Почему прежняя спекулятивка могла тормозить

Это список подтверждённых свойств кода, **не распределение измеренных потерь**:

- При C80/W8 target verification обрабатывает 640 токенных позиций, а обычный
  decode при B80 — 80. Ускорение зависит от реально принятых токенов и стоимости
  всей speculative-итерации. Humming ускоряет MoE, но не отменяет остальные этапы.
- Bounded draft синхронно переносит принятые K/V в CPU backing. Этот перенос
  сохранён: его завершение требуется текущей схеме восстановления HiCache.
  Continuity fast path убирает повторную проверку окна, но не этот перенос.
- Повторные boolean-index операции вызывают определение размеров результата
  через nonzero на CUDA. Их дублирование убрано; одна compaction остаётся.
- При недостатке памяти upstream может отключить draft-граф. При выходе батча
  за размер захваченных графов возможен eager fallback. Теперь это видно
  отдельно для draft, target verification и selector; `require` останавливает
  такой запуск с понятной ошибкой.
- При sampling DFlash2 строит также плотный буфер вероятностей draft по всему
  vocabulary. Для B80/W8/V154880 его минимальный размер — около 331 MiB на rank;
  прочие target/sampling buffers добавляются отдельно. Это не FP8 KV-кэш.

Новый патч **не объявляет всю прежнюю деградацию исправленной**. Для этого нужен
замер на GPU с текущим Humming и той же нагрузкой. Старый GSM8K accept length
при C1 не является прогнозом для C80.

## Сборка

Из распакованного проверенного архива:

```bash
cd glm53-hicache-v9.12-release
bash build.sh --push
```

Результат:
`i501-harbor-infra.ai.turbocloud.ru/images/lmsysorg/sglang:glm53-hicache-v9.12-0bcd822377da`.
Без `--push` образ только собирается и проверяется локально. Сборка образа здесь
не выполнялась. `BASE_IMAGE` в Dockerfile ссылается на v9.10; не подменяй его
неизвестным patched image — installer допускает только проверенные хэши v9.10,
закреплённого upstream и текущего патча.

## Манифесты

Все используют существующий Deployment `sglang-glm53-dcp4` в `inf-glm53`,
стратегию Recreate и те же восемь GPU на `i501-infcp-prod-k8s-w06`.
PVC и Service уже должны существовать. Применять **по одному**; дополнительные
реплики или сервер с моделью параллельно не нужны.

| Файл | Назначение |
|---|---|
| `05-humming-c80-nospec.yaml` | Основная база: CP8/DCP4 + Humming + HiCache, speculation off |
| `06-humming-c80-dflash.yaml` | Та же топология, DFlash2/W8/window2048; требует использования обоих графов и selector в графе |
| `07-humming-c80-dflash-profile.yaml` | Диагностика DFlash: 32 завершённых измерения при B≥80, графы в режиме warn |
| `08-humming-c80-eagle-tp8.yaml` | Штатный EAGLE/MTP: TP8/EP8/DCP1, CP off, target Humming, draft stock CUTLASS, 3 steps/topk1/4 target rows на запрос |
| `09-humming-c80-tp8-nospec.yaml` | База для сравнения EAGLE: та же топология и параметры, speculation off |

В EAGLE-паре prefill backend — `flashmla_kv`, prefill graphs выключены.
Это отдельный нативный профиль: скорость prefill и ёмкость KV будут другими.
Сравнивай **06 с 05**, а **08 с 09**. Оценивать пользу EAGLE сравнением 08 с 05
нельзя: одновременно меняются CP/DCP и prefill.

Для native MTP используется тот же локальный полный W4AFP8 checkpoint,
содержащий MTP-веса. `incoai/GLM-5.3-DFlash2` не подходит в качестве EAGLE draft.
Если checkpoint опубликован без MTP, launcher остановится до загрузки весов.
Значения topk1 и steps3 — начальный явный профиль, не результат autotuning.
Можно менять steps вместе с `speculative-num-draft-tokens = steps + 1`.

## Запуск и возврат

На хосте с kubectl, из каталога архива:

```bash
kubectl -n inf-glm53 apply -f manifests/06-humming-c80-dflash.yaml
kubectl -n inf-glm53 rollout status deployment/sglang-glm53-dcp4 --timeout=120m

NS=inf-glm53
POD=$(kubectl -n "$NS" get pod -l app=sglang-glm53-dcp4 -o jsonpath='{.items[0].metadata.name}')
kubectl -n "$NS" exec "$POD" -c sglang -- cat /opt/glm53-cp8-dcp4-v1/REVISION.json
kubectl -n "$NS" logs "$POD" -c sglang | grep -E 'glm53:|GLM53 DFLASH|bounded draft|DFLASH.*graph'
```

Отключение DFlash на том же образе:

```bash
kubectl -n inf-glm53 apply -f manifests/05-humming-c80-nospec.yaml
kubectl -n inf-glm53 rollout status deployment/sglang-glm53-dcp4 --timeout=120m
```

Полный возврат к v9.10: применить сохранённый рабочий C80-манифест v9.10.
При ручном редактировании speculation off означает удалить все `--speculative-*`,
поставить `--glm53-draft-cache-window 0` и убрать DFlash diagnostic options.
Launcher сбрасывает DFlash-флаги окружения при выборе другого режима.

## Диагностика задержек

В обычном режиме 06 подробный замер выключен. Профиль 07 сохраняет CP/DCP,
Humming, bounded cache и C80, но собирает небольшой отчёт в логе:

```bash
kubectl -n inf-glm53 apply -f manifests/07-humming-c80-dflash-profile.yaml
kubectl -n inf-glm53 rollout status deployment/sglang-glm53-dcp4 --timeout=120m
```

Запусти тот же короткий C80-бенч. Затем на хосте с kubectl:

```bash
NS=inf-glm53
POD=$(kubectl -n "$NS" get pod -l app=sglang-glm53-dcp4 -o jsonpath='{.items[0].metadata.name}')
kubectl -n "$NS" logs "$POD" -c sglang | grep 'GLM53 DFLASH' > glm53-dflash-c80-stages.log
```

В отчёте `GLM53 DFLASH profile`:

- `prepare`: подготовка блока, окна draft, embedding и параметров sampler;
- `draft`: draft forward и предложение токенов/selector;
- `verify`: target forward и применение ограничений к logits;
- `accept`: приёмка, bonus и обновление длин;
- `cache`: projection target features в шесть draft K/V слоёв, CPU backing и ring;
- `mean_committed_tokens_per_request`: среднее количество выданных токенов за
  итерацию, с bonus по семантике `commit_lens`.

Измеряется rank0. CUDA events дают **время между отметками на рабочем stream**,
включая ожидания и промежутки между запусками; это не сумма длительностей kernels.
CPU и GPU времена перекрываются, их нельзя складывать. Сборщик читает pinned
CPU tensor только после `event.query()`, не добавляет `synchronize()` и держит
не более четырёх незавершённых образцов. Часть образцов может быть пропущена,
если очередь занята. Итог появляется после завершения 32 образцов и следующего
опроса; если B80 не достигается, уменьши `--glm53-dflash-profile-min-bs` явно.
Замер сам добавляет overhead; финальную производительность проверяй в 06.

Для скорости нужно, чтобы полная speculative-итерация / среднее число выданных
токенов была быстрее обычного decode **при том же B и контекстах**. Для 2k tok/s
при 80 реально активных запросах это около 40 ms эффективного времени на токен.
Это условие, не прогноз результата.

## Бенч и точность

Внутри pod с vLLM benchmark — прежний короткий тест с C80. Остальные параметры,
включая server-default temperature, не меняются:

```bash
vllm bench serve \
  --backend openai-chat \
  --endpoint /v1/chat/completions \
  --base-url http://sglang-glm53-dcp4.inf-glm53.svc:8080 \
  --model GLM-5.3 \
  --num-prompts 400 \
  --max-concurrency 80 \
  --request-rate inf \
  --save-result --save-detailed \
  --result-dir /results \
  --result-filename glm53-v912-humming-dflash-c80.json \
  --dataset-name random \
  --random-input-len 1000 --random-output-len 1000 \
  --tokenizer PhalaCloud/GLM-5.3-W4AFP8 \
  --percentile-metrics ttft,tpot,itl,e2el \
  --metric-percentiles 50,90,95,99
```

Для 05/08/09 меняй имя файла. Не добавляй temperature=0 только в одну сторону
сравнения: это меняет путь DFlash sampling и нагрузку.

Внутри SGLang pod — прежний GSM8K для каждого выбранного speculative-режима:

```bash
python3 -m sglang.test.run_eval \
  --eval-name gsm8k --host 127.0.0.1 --port 8080 --model GLM-5.3 \
  --num-examples 200 --num-shots 5 --num-threads 1 \
  --temperature 0 --max-tokens 4096 \
  --chat-template-kwargs '{"enable_thinking":false}'
```

GSM8K при C1 не проверяет C80, sampling и HiCache loadback. Для GPU приёмки
нужны также C80 запросы, повторяющиеся длинные префиксы, отсутствие NaN/ошибок,
приёмка токенов и восстановление L2. Host-тесты проверяют соответствующую логику,
но не заменяют этот запуск. Дополнительный сервер с полной моделью не требуется.

## Проверено здесь

- 126 host/chunk тестов, 183 subtests: пройдены.
- CPU-проверки C80/W8, перехода ring через границу, отброшенных proposal-строк,
  порядка projection/norm/RoPE, L2 relocation, prefix reuse и повторного использования
  виртуальных IDs: пройдены с CPU tensor substitutes.
- Новая диагностика: ограничение очереди, запрет чтения до completion event,
  graph-policy, выключенный замер и отдельный ранг проверены с fake CUDA events.
- Полноценной GPU-валидации Humming+DFLASH или native EAGLE, сборки образа,
  GSM8K и замеров ускорения в этой среде не было.
