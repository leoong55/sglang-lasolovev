# v9.10 — Humming EP heuristic and bounded CP prefill padding

Base: `6bd52126422de3671558f3e412bba0cd57188aa8` (v9.9 / PR #12).

The C40 profile has 32.32 ms between ordinary decode steps, 31.87 ms inside
the GPU graph, and 10.59 ms of expert GEMMs. A faster scheduler cannot remove
that GPU time. This patch does not promise 2000 output tokens/s.

* Standard EP8 Humming now estimates 40 local assignments at C40, instead of
  320 global slots. This selects Humming 0.1.12's block-M 8 instead of 24 for
  the GLM gate/up and down shapes. It changes the launch heuristic only:
  actual GPU routing and allocation bounds still cover every input slot.
  DeepEP and other Humming quantization integrations are unchanged.
* CP8 prefill may reuse the nearest captured bucket with at most 25% padding.
  16192 -> 16384 and 7084 -> 8192 qualify; 1012 -> 8192 does not. Logical
  request lengths, positions of real tokens, DCP plans and KV allocation are
  unchanged. CP gather discards physical tails before KV/DSA writes and logits.
* `SGLANG_GLM53_HUMMING_EP_AWARE=0` restores the previous Humming heuristic.
  `SGLANG_GLM53_PREFILL_BCG_PADDING=0` restores exact-only prefill graph reuse.
  Set these in the manifest and restart; they are not live API controls.

## Build and single-node use

```bash
tar -xzf glm53-hicache-v9.10-release.tar.gz
cd glm53-hicache-v9.10-release
bash build.sh --push
kubectl apply -f manifests/02-humming.yaml
kubectl -n inf-glm53 rollout status deployment/sglang-glm53-dcp4 --timeout=7200s
```

The manifest uses the existing Deployment and eight GPUs with Recreate.
It retains CP8/DCP4, HiCache, FP8 KV, graph bucket 40 and disabled speculation.
It does not add another serving replica. It preserves the working node affinity to i501-infcp-prod-k8s-w06.

Look for `humming-ep-aware=1; prefill-padding=1` in the launcher log and
`GLM53 BCG replay=... global_tokens=16384 local_rows=2048 raw_tokens=16192`
when that batch geometry is scheduled. The replay counter logs first/every
100th replay, so an absent particular batch size in logs is not proof of a miss.

## Optional kernel correctness gate on the same GPUs

Apply `manifests/00-kernel-check.yaml` instead of the serving manifest, then
inside that sleeping pod run:

```bash
torchrun --standalone --nproc-per-node=8 \
  /opt/glm53-cp8-dcp4-v1/benchmarks/check_w4_humming_gpu.py \
  --model-path /mnt/model-pvc-w4fp8 --batches 8 40 48 \
  --compare-ep-heuristic --output /mnt/cache/glm53-v910-kernel-check.json
```

This loads one real MoE layer, captures both heuristics with one Humming
weight set, changes inputs/routes, includes zero-work peers, and compares
against an independent dequantized reference. It measures the local MoE,
not full-model throughput. Reapply `manifests/02-humming.yaml` afterwards.
Recheck GSM8K and the 60k-prefix workload after any graph or kernel change.

Host validation passed (89 host tests and 28 chunk/geometry tests); GPU correctness, CUDA
capture of padded production requests, image build and speed remain untested
here. In particular the CPU poison-padding tests exercise real gather code
with a simulated collective, not CUDA attention.
