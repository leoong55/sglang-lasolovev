# GLM-5.3: зафиксированный результат 11 сентября 2026

Текущий запуск завершил **300 запросов без ошибок**, выдал 300 000 токенов
за 545,78 с: **549,67 output tok/s**. Это лучший общий throughput среди
найденных результатов той же полной GLM-5.3 в
[исходной переписке](https://chatgpt.com/share/6aa4237b-3cc0-83ed-b106-2d01e5e223d8).
GLM-5.3-Flash в сравнение не включена.

Полные 31 метрика каждого прогона сохранены без пересчёта в
[historical-results.json](historical-results.json) и
[2026-09-11-v9.4.json](2026-09-11-v9.4.json). Исторические результаты взяты
из сообщений пользователя; названия версий восстановлены по окружающей
переписке. В JSON сохранены время сообщения и источник каждого результата.

## Сопоставимость

Во всех восьми прогонах совпадают 300 успешных запросов, 0 ошибок,
клиентский concurrency 40, 22 503 605 входных и 300 000 выходных токенов.
В исходной команде использовались `prefix_repetition`, 20 префиксов,
60k prefix + 15k suffix, 1000 выходных токенов, один warmup, бесконечная
скорость подачи, `ignore-eos`, temperature 0.3 и reasoning enabled.

Это сильная основа для сравнения общей нагрузки. Точная команда нового
прогона, версия клиента, исходный JSON с деталями, digest образа и effective
argv Pod не приложены. Холодное/прогретое состояние кешей не зафиксировано.
Повторные прогоны для оценки разброса отсутствуют.

Последний подготовленный профиль v9.4: TP8/EP8/CP8, DCP4 ag_rs, target FP8,
DFlash2/FA4 с BF16 draft KV, HiCache write_through, A2A none, chunk 16k,
max-running 32, mem-fraction 0.75. Снимок находится в
[v9.4-prepared-manifest.yaml](v9.4-prepared-manifest.yaml); это подготовленный
манифест из commit `1a03ba2a2501d6086aa3b864a28008883963fefa`, а не выгрузка
фактически применённого Pod. Его старая annotation v9.3 сохранена как была;
тег образа в нём v9.4.

медиана TTFT стала заметно хуже, P95 также вырос. Средний TTFT почти тот же.

по себе не объясняет регрессию между версиями. Нужны одинаковые лимиты,
состояние кеша и подробные временные отметки для сравнения.

## Почему peak меньше среднего, а ITL больше TPOT

Средний output throughput сходится с итоговыми числами:
`300000 / 545.78 ≈ 549.67 tok/s`.

В просмотренной реализации
[vLLM OpenAI chat client](https://github.com/vllm-project/vllm/blob/main/vllm/benchmarks/lib/endpoint_request_func.py)
ITL записывается на полученное SSE-сообщение с `choices`, а число итоговых
токенов берётся из `usage.completion_tokens` при наличии.
[Агрегатор benchmark](https://github.com/vllm-project/vllm/blob/main/vllm/benchmarks/serve.py)
восстанавливает пиковую скорость из TTFT и этих интервалов, считая каждое
событие одним токеном. Если DFlash отправляет несколько токенов одним
сообщением, средняя и «пиковая» скорости фактически измеряют разные вещи.

Это объяснение по коду клиента, а не подтверждение точной версии клиента
оператора: версия не приложена. Оно согласуется с peak 453 при среднем
549.67 и ITL mean 170.80 при TPOT mean 47.78. Сравнивать такой ITL напрямую
с интервалом между отдельными токенами прежнего запуска нельзя. При этом
P95 ITL 806 мс и P99 1000 мс всё равно указывают на длинные паузы между
событиями потока; для интерактивного ответа их стоит измерять отдельно.

Та же реализация оценивает peak concurrent requests по целым секундным
интервалам. Запросы, завершившиеся и начавшиеся внутри одной секунды,
могут попасть в один бакет, даже если не пересекались во времени. Поэтому
peak 44 сам по себе не доказывает нарушение клиентского лимита 40 или
серверного max-running 32.

## Следующее сравнение с v9.5

1. Запустить базовый v9.5 с прежними настройками и сохранить effective argv,
   image digest, версию `vllm`, подробный результат, acceptance и cache counters.
2. Отключить только DFlash, сохранив max-running 32, HiCache, chunk 16k и
   одинаковое состояние кешей: `manifest-nospec-32.yaml`.
3. Для выбранного режима увеличить max-running и decode graph max BS до 64.
   Сначала сохранить клиентский concurrency 40; отдельным тестом проверить 64.
4. Сравнивать холодные и прогретые кеши отдельно. Успешный benchmark ещё
   не подтверждает численную эквивалентность и принудительный round-trip
   KV/indexer/draft через RAM; эти проверки остаются в README.

## Историческая команда нагрузки

Восстановлена из пользовательского сообщения в исходной переписке.
Точную идентичность команды текущего прогона не предполагаем.

```bash
vllm bench serve \
  --backend openai-chat \
  --base-url http://sglang-glm53-dcp4.inf-glm53.svc:8080 \
  --endpoint /v1/chat/completions \
  --model GLM-5.3 \
  --tokenizer PhalaCloud/GLM-5.3-W4AFP8 \
  --dataset-name prefix_repetition \
  --prefix-repetition-prefix-len 60000 \
  --prefix-repetition-suffix-len 15000 \
  --prefix-repetition-output-len 1000 \
  --prefix-repetition-num-prefixes 20 \
  --request-rate inf --max-concurrency 40 \
  --num-prompts 300 --num-warmups 1 \
  --ignore-eos --temperature 0.3 \
  --extra-body '{"chat_template_kwargs":{"enable_thinking":true}}' \
  --percentile-metrics ttft,tpot,itl,e2el \
  --metric-percentiles 50,95,99 \
  --save-result --save-detailed --result-dir /results \
  --result-filename glm53-dcp4-c40-prefix20.json
```

Для новых прогонов меняйте имя результата, чтобы сохранить каждый вариант.
