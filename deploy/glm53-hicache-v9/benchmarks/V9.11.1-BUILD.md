# v9.11.1 — sequential CUTLASS compilation

The v9.11 image build put all seven template instantiations in one `.cu` file.
On the reported builder (7680 MiB RAM, no swap), one `cicc` process consumed
about 6.5 GiB and available memory fell to about 41 MiB. Heavy memory reclaim
and I/O wait explain the stalled build. `No CUDA runtime is found` was not the
cause: CUDA compilation was already running.

## Changes

- Each of the seven variants now has its own `variant_N.cu`. The operator
  registration/validation is a separate `.cpp` with no CUTLASS templates.
- `MAX_JOBS=1` is forced, including when the base image exports a larger value.
  One variant completes and its compiler exits before another starts.
- The seven IDs, tile/schedule/cluster choices, SM90a target, optimization flags,
  upstream mainloop/scale layout and all `python/sglang` files are unchanged.
- Download, SHA256 check, extraction, compilation and registration have explicit
  logs. A heartbeat prints every 15 seconds during long stages. A heartbeat
  indicates that the build process is alive; it does not prove useful progress.
- Downloads use a `.part` file and streaming SHA256. An interrupted/bad transfer
  cannot be reused as a completed archive. The 120 s URL timeout is a socket
  timeout, not a deadline for the entire transfer.
- `--humming-only` omits the optional tuning extension and downloads no CUTLASS
  source. It retains patch 1 and the already-installed stock CUTLASS backend.
  It uses a distinct image tag and serving manifest.

Splitting reduces simultaneous template instantiation; it is **not** a measured
RAM ceiling. A single variant could still exceed a small builder's available
memory. We have not measured its nvcc peak, compiled/linked with nvcc, built the
image or tested the CUDA kernels here. No additional GPUs are needed to build.

## Both patches, including all seven CUTLASS tuning candidates

Stop the old build first; do not run both builds on the 8 GiB host at once.
Extract into a new directory so old sources/artifacts cannot contaminate it:

```bash
tar -xzf glm53-hicache-v9.11.1-release.tar.gz
cd glm53-hicache-v9.11.1-release
bash build.sh --push
```

Image:
`i501-harbor-infra.ai.turbocloud.ru/images/lmsysorg/sglang:glm53-hicache-v9.11.1-0bcd822377da`

The build prints the source names, Ninja commands/completed jobs, a heartbeat,
and finally `Build complete; all seven variants are included`. `build.sh`
then verifies the runtime overlay and, in a fresh CPU-only container, the image
flavor, library SHA256 and operator registration before pushing. `BUILD.json`
records enabled=true, variants=7, build_layout=one-variant-per-cu and max_jobs=1.

Use the existing tuning cycle in [V9.11-VALIDATION.md](V9.11-VALIDATION.md).
Manifests `00-kernel-check.yaml`, `01-cutlass.yaml`, `02-humming.yaml` and
`03-cutlass-tuned.yaml` point to this full image. No image rebuild is needed
when changing between Humming and stock/tuned CUTLASS in this full image.

## Humming + padding, without the optional CUTLASS compilation

From the same extracted directory:

```bash
bash build.sh --humming-only --push
kubectl -n inf-glm53 apply -f manifests/04-humming-only.yaml
kubectl -n inf-glm53 rollout status deployment/sglang-glm53-dcp4 --timeout=7200s
```

Image:
`i501-harbor-infra.ai.turbocloud.ru/images/lmsysorg/sglang:glm53-hicache-v9.11.1-humming-only-0bcd822377da`

This flavor is for patch 1/stock serving. Do not run the tuning benchmark or
set `SGLANG_GLM53_CUTLASS_CONFIG` on it: the seven-candidate library is absent.
`BUILD.json` explicitly records enabled=false and variants=0. The original
Triton preflight still runs in either flavor; it finished in 13 s in the supplied
build log and is independent of the failed CUTLASS compilation step.

## Verify locally

From the repository checkout (Python, torch, pytest installed):

```bash
export SGLANG_SOURCE_ROOT="$PWD"
python3 -m pytest -q deploy/glm53-hicache-v9/tests/test_host_cutlass_build.py \
  deploy/glm53-hicache-v9/tests/test_host_cutlass_tuning.py
```

These host checks cover the split wrapper linkage/variant mapping using a C++
stub, interrupted/corrupted downloads, sequential job settings, build failure
and flavor/tag/verification behavior. They cannot validate nvcc/CUTLASS code
generation, CUDA linkage or the GPU memory/performance/correctness gates.

Executed locally: **9 tests and 14 subtests passed**, plus Python/shell syntax,
five manifest image/resource checks and parity between the two Humming serving
manifests. GPU test scripts are now included in the image build context as well
as the archive (the old Docker ignore rule excluded the `tests` directory).

For comparison with the user-designated pre-patch baseline (400 requests, C40,
1102.37 output tok/s, mean TPOT 35.13 ms), remember that baseline lacked the
batch-40 decode graph. These serving manifests include it. Report its effect
separately or align the buckets before attributing gains to patch 1/2.
