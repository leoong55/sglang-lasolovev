# P1 / v9.9: Humming для W4 MoE при сохранении CP8/DCP4

Патч основан на запущенном v9.8: `2aa3716d0e9f4d55dca0e5c31dbef2b8c55a3dcf`.
Цель — проверить альтернативную реализацию крупного компонента decode.
Полученные 957/1197 tok/s без CP с/без DCP показывают цену DCP, но даже без него
TPOT=30,64 мс. Патч не обещает 2000 tok/s и не меняет scheduler.

## Что меняется

- `--quantization w4afp8 --moe-runner-backend humming` выбирает Humming **только для MoE**.
- `--moe-runner-backend cutlass` либо прежний `auto` сохраняют прежний W4 путь.
- Dense FP8, MLA/DSA, CP8/DCP4, FP8 KV, Q8 prefill и HiCache используют прежний код.
- Загрузка experts и input scales выполняется прежним W4 loader, с прежним EP mapping.
  После загрузки signed INT4 переупаковывается в представление Humming с сохранением
  весовых значений и групповых scales. Конвертируется один sublayer, постоянной второй
  копии experts в сервере нет. Во время преобразования нужна временная память.
- В Humming используются динамические FP8 scales активаций на токен; в CUTLASS —
  статические scales checkpoint. Поэтому требуется оценка точности, а не требование
  полного совпадения всех генерируемых токенов. Это отличие явно записывается в лог.
- Runner остаётся живым между вызовами. Стандартная обёртка Humming, создающая
  временный runner при каждом вызове, обходится через штатные pre/post-permute.
- Начальная область проверки: SM90, BF16 activations, A2A none, SiLU, отдельные shared
  experts, DFlash off. CUDA-ошибки не маскируются автоматическим откатом на CUTLASS.

## Сборка

Готовый release-архив уже содержит полный overlay всех предыдущих патчей из этой
ветки, installer, проверки и манифесты. DeepEP-ветка v6 в него не добавляется.

```bash
tar -xzf glm53-hicache-v9.9-release.tar.gz
cd glm53-hicache-v9.9-release
bash build.sh --push
```

Результат:
`i501-harbor-infra.ai.turbocloud.ru/images/lmsysorg/sglang:glm53-hicache-v9.9-0bcd822377da`.
База — прежний `v0.5.19-latest-0bcd822377da`; installer проверяет SHA-256 исходников.
Humming 0.1.12 уже указан в зависимостях upstream. Docker проверяет его наличие и API;
если внутренний базовый образ отличается, сборка остановится, а не обновит Torch/CUDA.

Для сборки из PR checkout с доступными commits базовой цепочки:

cd ../glm53-hicache-v9.9-release

## Проверка одного реального MoE-слоя на тех же восьми GPU

Дополнительные GPU не нужны. Сохранить свой рабочий Deployment-манифест для возврата.
На хосте с kubectl применить вариант со sleep вместо сервера. API будет недоступен
до запуска одного из serving-манифестов. Service и PVC остаются существующими.

```bash
kubectl apply -f manifests/00-kernel-check.yaml
kubectl -n inf-glm53 rollout status deployment/sglang-glm53-dcp4 --timeout=7200s
set -o pipefail
kubectl -n inf-glm53 exec deployment/sglang-glm53-dcp4 -c sglang -- \
  torchrun --standalone --nproc-per-node=8 \
  /opt/glm53-cp8-dcp4-v1/benchmarks/check_w4_humming_gpu.py \
  --model-path /mnt/model-pvc-w4fp8 --checkpoint-layer 3 \
  --batches 1 8 40 48 2048 --iterations 50 \
  --output /tmp/glm53-w4-humming.json \
  2>&1 | tee glm53-w4-humming-gpu.log
```

Проверка читает только routed experts одного слоя через `model.safetensors.index.json`.
Каждый ранг загружает свои 32 experts через настоящий W4 weight loader. Две реализации
получают одинаковые веса, входы и маршруты. Полная модель не загружается. Вариант
`--synthetic` предназначен только для проверки механики, его нельзя выдавать за
проверку вашего checkpoint.

Проверяются:

- signed INT4/group scales через независимую деквантизацию и FP32 расчёт;
- eager и CUDA graph с изменившимися входами, probabilities и expert IDs;
- концентрированная маршрутизация, при которой семь рангов не имеют локальных tokens;
- корректность локального результата и его суммы по EP8;
- конечность чисел; относительная L2 к FP32 не выше 0,08; graph/eager rtol=0,001,
  atol=0,002. Это порог компонентной проверки, не гарантия качества модели.

Таймер считает local dispatch, quantization, GEMM, SiLU, combine. Он исключает
attention, shared expert, EP all-reduce, scheduler и prefill/decode смешанной нагрузки.
JSON содержит все восемь рангов и отдельные отсчёты; сравнивать следует также медленный
ранг, а не только rank0. Успех компонента не доказывает выигрыш сервера.

Забрать результат через хост:

```bash
POD=$(kubectl -n inf-glm53 get pods -l app=sglang-glm53-dcp4 \
  --field-selector=status.phase=Running -o jsonpath='{.items[0].metadata.name}')
kubectl -n inf-glm53 cp -c sglang "$POD:/tmp/glm53-w4-humming.json" ./glm53-w4-humming.json
```

При ошибке проверку не считать пройденной. Для возврата сервера применить
`manifests/01-cutlass.yaml` либо свой сохранённый рабочий манифест.

## Сравнение серверов и точность

В обоих serving YAML: CP8/DCP4, HiCache write_through, mem=0.80, max-running=48,
prefill=16k/Q8/breakable, full decode graphs с отдельным bucket 40. DFlash и
экспериментальный all-reduce fusion выключены. Между двумя YAML меняются только
backend и название профиля. Это новая парная база: старые прогоны с другим fusion
или bucket нельзя считать строгим контрольным измерением.

```bash
kubectl apply -f manifests/01-cutlass.yaml
kubectl -n inf-glm53 rollout status deployment/sglang-glm53-dcp4 --timeout=7200s
```

После компонентной проверки Humming и при наличии выигрыша на нужных batch sizes:

```bash
kubectl apply -f manifests/02-humming.yaml
kubectl -n inf-glm53 rollout status deployment/sglang-glm53-dcp4 --timeout=7200s
```

В startup-логе Humming нужен текст `W4AFP8 MoE: Humming`, а в effective argv —
`--quantization w4afp8 --moe-runner-backend humming`. Сохранить размер фактически
выделенного KV, память, ошибки и сообщения о CUDA graphs.

На каждой из двух конфигураций повторить тот же GSM8K:

```bash
kubectl -n inf-glm53 exec deployment/sglang-glm53-dcp4 -c sglang -- \
  python3 -m sglang.test.run_eval --eval-name gsm8k --host 127.0.0.1 --port 8080 \
  --model GLM-5.3 --num-examples 200 --num-shots 5 --num-threads 1 \
  --temperature 0 --max-tokens 4096 \
  --chat-template-kwargs '{"enable_thinking":false}'
```

Прежняя точка — 199/200. Сравнить изменившиеся ответы; 200 коротких примеров не
проверяют длинный контекст и HiCache loadback. Скрипт ниже запускать в бенч-поде
поочерёдно для каждой конфигурации с соответствующей меткой:

```bash
bash bench-w4.sh cutlass short
bash bench-w4.sh humming short
```

Если выигрыш воспроизводится и точность приемлема — основной длинный сценарий
60k prefix +15k suffix +1k output, 20 prefixes, C40:

```bash
bash bench-w4.sh cutlass long
bash bench-w4.sh humming long
```

Эти четыре команды выполняются при соответствующем запущенном backend, не подряд
на одной конфигурации. Перед длинным тестом каждого backend перезапустить сервер
применением нужного манифеста после другой конфигурации: одинаковая исходная теплота
cache. Никакие cache-flush или изменения production через kubectl patch не требуются.

Профилирование во время бенчей выключено. Фиксировать throughput, TPOT, TTFT/ITL
P95/P99, KV-ёмкость, число ошибок. Не принимать ускорение короткого теста ценой
существенного ухудшения основного prefill-сценария.

## Что проверено при подготовке

86 CPU host tests прошли на Torch 2.9.1+cpu, включая 7 новых проверок. Реальные
CPU tensor operations проверяют signed packing, scales и независимый reference;
CUDA-зависимые части импортов/transform в unit-тестах заменены fixtures.
Humming 0.1.12 импортируется, API проверен. Манифесты и Python/shell синтаксис проверены.
Docker build, GPU kernels, полный запуск модели, качество и производительность
здесь не проверялись — для этого подготовлены команды выше.
