# v9.13: исправление допуска draft-графов и управляемый размер verify

Кандидат поверх v9.12 `3e2b2c5c5176fbf665631b6a1f4961b337707965`.
Это исправление подтверждённого дефекта и возможность уменьшить дорогой verify.
Ускорение на H200 ещё не измерено; обещания 2× нет.

## Что установлено по последнему логу

Источник: предоставленный оператором `Вставленный текст(20260914-101850).txt`.
GSM8K выполнялся позже профиля; это разные измерения, их нельзя смешивать.

| GSM8K, 200 примеров, 5-shot, temperature=0 | C1 | C20 |
| --- | ---: | ---: |
| Score | 0.990 | 0.990 |
| Средняя длина принятого блока | 5.2991 | 5.2673 |
| Время, с | 370.432 | 104.899 |
| Выходных токенов/с | 112.566 | 395.751 |

На этих данных нет обвала принятия токенов при переходе C1→C20. Это не проверка
вероятностного режима на C40/C80, длинного контекста или восстановления HiCache.

Отдельный профиль ранга 0, C40, блок 8, 32 итерации:

| Стадия | Время на потоке, мс/итерацию | Доля |
| --- | ---: | ---: |
| Prepare | 1.309 | 1.38% |
| Draft | 10.887 | 11.47% |
| Target verify | 80.333 | 84.65% |
| Accept | 1.284 | 1.35% |
| Cache | 1.092 | 1.15% |
| Всего | 94.905 | 100% |

Принято в среднем 2.9258 токена/запрос/итерацию; отношение 94.905 / 2.9258 =
32.437 мс/выходной токен в этом фрагменте. Это не TPOT всего бенчмарка.
CUDA events измеряют время потока, включая паузы запуска и ожидания; это не
сумма длительностей GPU-ядер и не максимум по восьми рангам.

`host_elapsed_ms.cache=79.253` нельзя считать 79 мс копирования KV: CPU доходит
сюда, пока verify ещё выполняется, и ждёт его завершения. На потоке стадия cache
заняла 1.092 мс. Переписывание HiCache ради этих 79 мс не обосновано.

Даже полное устранение всех 10.887 мс draft при неизменных остальных стадиях
даст только 94.905 / 84.018 = **1.13×**. Для 2× при неизменных прочих затратах
verify должен сократиться примерно с 80.33 до 32.88 мс. Исправление draft-графов
не является достаточным объяснением или решением всей деградации.

## Подтверждённый дефект

В логе `draft_graph=False`, `verify_graph=True`, `sampler_in_graph=False`
встречаются и для 1/8/32 запросов. Поэтому отсутствие бакета 40 не объясняет
отказ всех draft-графов.

Цепочка в исходниках:

1. `arg_groups/model_overrides/deepseek_v2.py`: для DSA + prefill CP внутренний
   `enable_dp_attention=True` включает синхронизацию MLP, в том числе при CLI DP=1.
2. `DecodeCudaGraphRunner` проверяет разрешение планировщика
   `ForwardBatch.can_run_decode_cuda_graph`, если `require_mlp_sync=True`.
3. Target получает его через `ForwardBatch.init_new()` и
   `init_mlp_sync_metadata()`. DFlash создавал свой draft `ForwardBatch` вручную,
   оставляя разрешение `False` и не передавая счётчики запросов.
4. v9.13 передаёт разрешение и вызывает тот же штатный метод подготовки
   метаданных. Счётчики запросов сохраняются отдельно от счётчиков токенов,
   умноженных на размер блока.

Регрессионный тест исполняет реальные конструктор, метод метаданных и метод
допуска графа на CPU. Старое состояние запрещает каждый проверяемый бакет;
исправленное допускает подходящие размеры. Отрицательное решение планировщика,
превышение ёмкости, несовпадение ширины и запрет padding остаются действующими.
Проверка допуска не подтверждает корректность CUDA replay: это отдельная
проверка на H200, которой здесь не было.

## Остальные изменения

- Логи показывают реальные размеры replay draft/target, логические строки
  verify, флаг планировщика и причину отказа. Сообщение о регистрации capture
  hook больше не утверждает, что граф уже используется. Диагностика читает
  только host metadata; дополнительных `.item()`/GPU→CPU-копий в ней нет.
- Актуальные манифесты 05–10 включают decode-бакет 40. При C40/W8 прежний
  набор округлял replay до C48: 384 строки вместо 320. Новый бакет убирает
  64/384 = 16.7% строк padded-батча; это не обещание 16.7% ускорения.
  Для строгого A/B изменения кода используйте одинаковые бакеты на обеих версиях.
- В манифестах DFlash политика графов — `warn`. Отсутствие подходящего графа
  позволяет eager fallback. Проверки корректности размеров и самого рантайма
  сохраняются; CUDA-ошибки не скрываются. `require` остаётся явной опцией.
- Bounded draft поддерживает блоки **2/4/8**, default **8**, окно **2048**.
  Блок 4 — отдельный экспериментальный манифест 10, не автоматическое изменение.
  Это использует существующий `--speculative-dflash-block-size` и штатный
  `DFlashDraftModel.set_block_size`, включая обе свёртки каждого слоя.
  Блок 8 означает 7 предложений + проверяемый anchor; блок 4 — 3 + anchor.
- Отдельно проверены границы native grouped convolution между запросами,
  сохранение окна при переходе через страницу/оборот ring, отбрасывание scratch
  отвергнутых токенов и causal/ownership индексы verify при ширине 4.
  GPU-численная корректность новых размеров пока не подтверждена.

Уменьшение блока снижает число target-строк, но может снизить и число принятых
токенов. Сравнивать нужно `время полного цикла / принято токенов`, затем TPOT и
throughput на одинаковом трафике. У меньших блоков часть маленьких бакетов может
быть отфильтрована штатным CP-выравниванием; padding до следующего допустимого
бакета ожидаем. Графы не обязаны существовать ровно для каждого CLI-размера.

## Область повторного аудита

Проверен совокупный runtime-diff от `0bcd822377da`: 39 файлов, включая ранее
добавленные патчи, и смежные методы upstream, через которые эти изменения
исполняются. Это не заявление о проверке всех моделей и режимов всего SGLang.

| Участок | Проверенный контракт и решение |
| --- | --- |
| Launcher, arg hooks, graph capture | Явное выключение speculation; независимые лимиты запросов/графов; реальное разрешение планировщика вместо принудительного `True` |
| CP/BCG, сборка hidden states | Порядок токенов interleave, padding/causal lengths, захват вспомогательных target-слоёв; CP8 сохранён для длинного prefill |
| DCP gather, DSA page tables, LSE | Владение страницами, packed FP8 layout, выделение workspace, маски будущих токенов для каждой verify-строки; collectives не переписаны |
| DFlash2 selector и acceptance | Sparse draft probabilities передаются в `accept_sampling`; выбранный selector-путь не использует ветку fallback-to-greedy обычного draft без selector |
| FP8 KV и draft pool | Target FP8 отделён от BF16 FA4 draft; память фиксированного окна учитывается solver; схема window2048 сохранена |
| HiCache | `write_through/direct/layer_first`, producer-only DSA index, backing draft и завершение восстановления всех слоёв до использования окна |
| Humming | W4 MoE-адаптер, EP local/global expert counts и ёмкость буферов; backend не заменён; dense/attention не переводятся в Humming |

CPU-проверки этих контрактов не доказывают отсутствие GPU race/ошибок NCCL и не
заменяют проверку FA4/FlashMLA на реальных H200. Оснований отключать CP, менять
checkpoint или считать scheduler единственным виновником эти данные не дают.
По предыдущему A/B отключение CP ухудшало TTFT и не давало нужного выигрыша
decode. Переход на другой MoE backend тоже не исправит потерю scheduler metadata.

Target verify идёт через DSA/FlashMLA verify/decode-путь, поэтому смена только
`--dsa-prefill-backend` не ускорит его автоматически. Дальнейший дорогой патч
attention/MoE оправдан только после локализации времени **внутри** 80 мс verify.

EAGLE остаётся отдельным профилем TP8 без CP/DCP, с проверкой наличия native MTP
весов. Этот патч не объявляет EAGLE совместимым с CP8/DCP4. Для текущего
prefill-heavy сервиса основной профиль остаётся CP8/DCP4, Humming, HiCache.

## Сборка

В Dockerfile нет компиляции nvcc/CUTLASS. Основа — существующий v9.12; Python
overlay устанавливается только поверх файлов с известными SHA256. Установщик
также принимает точные файлы v9.10. Torch/CUDA/Humming в образе не обновляются.
Проверки CPU в CI используют отдельное окружение; оно не попадает в образ.

```bash
git clone --filter=blob:none \
  --branch work/glm53-dflash-graph-audit-v9-13 \
  https://github.com/leoong55/sglang-lasolovev.git glm53-v913-src
cd glm53-v913-src
python3 deploy/glm53-hicache-v9/make_bundle.py ../glm53-hicache-v9.13
cd ../glm53-hicache-v9.13
bash build.sh --push
```

Получится `i501-harbor-infra.ai.turbocloud.ru/images/lmsysorg/sglang:glm53-hicache-v9.13-0bcd822377da`.
Если builder имеет только v9.10, последнюю команду можно заменить на:

```bash
GLM53_BASE_IMAGE=i501-harbor-infra.ai.turbocloud.ru/images/lmsysorg/sglang:glm53-hicache-v9.10-0bcd822377da \
  bash build.sh --push
```

`REVISION.json` фиксирует source commit/tree. `make_bundle.py` требует committed
исходники; повреждённые/неизвестные файлы отклоняются до записи. Сборка образа
здесь не запускалась, значение `image_built_here=false` сохраняется.

## Первый запуск и короткая проверка

Начать с блока 8: так проверка исправления графов не смешивается с изменением
числа предложений. Манифест 07 включает только 32 измеряемые итерации при BS≥40;
06 — тот же профиль без измерения времени. Все Deployment имеют replicas=1 и
Recreate, используют существующие PVC и восемь GPU. Одновременно нужен один
профиль; применять команды следует в согласованное окно перезапуска сервиса.

С хоста с kubectl, из каталога собранного bundle:

```bash
kubectl apply -f manifests/07-humming-c80-dflash-profile.yaml
kubectl -n inf-glm53 rollout status deployment/sglang-glm53-dcp4 --timeout=7200s
kubectl -n inf-glm53 exec deployment/sglang-glm53-dcp4 -c sglang -- \
  cat /opt/glm53-cp8-dcp4-v1/REVISION.json
```

Проверка **изнутри runtime-пода**, без 200 примеров на этом первом шаге:

```bash
python3 -m sglang.test.run_eval \
  --eval-name gsm8k --host 127.0.0.1 --port 8080 --model GLM-5.3 \
  --num-examples 20 --num-shots 5 --num-threads 1 \
  --temperature 0 --max-tokens 4096 \
  --chat-template-kwargs '{"enable_thinking":false}'
```

20 примеров — smoke-проверка ответов/replay, не оценка точности с нужной
статистической силой и не тест HiCache loadback. После неё проверить с хоста:

```bash
kubectl -n inf-glm53 logs deployment/sglang-glm53-dcp4 -c sglang \
  | grep -E 'glm53:|GLM53 DFLASH (execution|graph inputs|profile):|Disable DFLASH'
```

На покрытом decode-размере ожидаются `draft_graph=True`, `verify_graph=True`,
`sampler_in_graph=True`. Startup-сообщение о регистрации hook этого не доказывает.
При `False` сначала посмотреть `reasons`/`scheduler_vote`/`capture_requests` в
новой строке `graph inputs`, не запускать ещё один длинный benchmark вслепую.

Затем дать обычный трафик с C40: профиль остановит сбор после 32 итераций,
рестарт для его остановки не нужен. Если draft исправлен, но отношение полного
цикла к принятому токену остаётся плохим, следующий **отдельный** опыт — блок 4:

```bash
kubectl apply -f manifests/10-humming-c80-dflash-block4-profile.yaml
kubectl -n inf-glm53 rollout status deployment/sglang-glm53-dcp4 --timeout=7200s
```

Повторить короткую проверку ответов и тот же C40-трафик. Не сравнивать greedy
GSM8K с random/temperature=0.3 как один workload. Графы требуют перезахвата после
изменения блока; image один и тот же. При отсутствии выигрыша доступен проверенный
вариант без speculation: `manifests/05-humming-c80-nospec.yaml`.

Для итогового принятия всё ещё нужны GPU-ответы, корректность длинного
контекста/HiCache restore и репрезентативный performance A/B. Их нельзя заменить
CPU-тестами или объявить пройденными по одному smoke-прогону. Но первичное
решение «работает ли исправленный путь» не требует очередного полного 400+300
бенчмарка.

## Проверки в окружении разработки

Пройдено: 111 host-тестов, 28 тестов конфигурации/chunk, 4 теста реальных
Triton-индексов/математики через CPU interpreter; 34 специализации SM90 успешно
скомпилированы. Проверены Humming 0.1.12 API и шесть актуальных манифестов
с checkpoint-geometry fixture. CI использует тесты актуального build kit:
архивный v7 запрещает padding, который намеренно добавлен в v9.10 и отдельно
проверяется текущим набором тестов.

Команды для воспроизведения CPU-проверок (Torch CPU; GPU отсутствует):

```bash
export SGLANG_SOURCE_ROOT="$PWD"
python -m unittest discover -s deploy/glm53-hicache-v9/tests -p 'test_host*.py'
python -m unittest discover -s deploy/glm53-hicache-v9/tests -p 'test_chunk*.py'
TRITON_INTERPRET=1 python -m unittest discover \
  -s deploy/glm53-hicache-v9/tests -p 'test_kernel*.py'

```

Зависимости CPU-проверок заданы в `.github/workflows/glm53-cp-host.yml`.
Triton interpreter проверяет индексы/математику на CPU; SM90 AOT проверяет
компиляцию, но не исполняет kernel на GPU. Фактические результаты и ограничения
также перечислены в описании PR.
