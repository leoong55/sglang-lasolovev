# GLM-5.3 W4AFP8: независимый эксперимент TP2 × PP4

Цель — проверить предложение из `H200.zip` на той же полной GLM-5.3 W4AFP8,
что использовалась в исследовании CP8/DCP4, с 40 активными тяжёлыми запросами.
Это экспериментальная сборка: CPU-проверки не подтверждают загрузку модели,
GPU-корректность, доступную ёмкость KV или преимущество в производительности.

База: `0bcd822377da7b5718e674eaf9c870d349424dd1`.
Ветка: `work/glm53-pp4-colleague`.
База PR: `work/glm53-upstream-0bcd822377da` — отдельная ссылка на исходный коммит.
Патчи CP/DCP/Q8 и DeepEP из v3/v5 в эту ветку не входят.

## Что перенесено из предложения коллеги

| Патч H200.zip | Реализация в этом варианте |
|---|---|
| 1: PP residual для `glm5_next.py` | Не применяется: полная `GlmMoeDsaForCausalLM` использует `deepseek_v2.py`; в базе уже передаются residual и indexer top-k между PP стадиями. |
| 2: chunking logits в KPool | Не применяется: файла KPool в базе нет; штатный `dsa_indexer.py` имеет собственный механизм chunking. |
| 3: SM120 TileLang FP8 | Не применяется к H200: сохраняется штатный `flashmla_kv`, без изменения соглашения о FP8 scales/layout. |
| 4: full-need admission | Перенесён с учётом всех PP микробатчей, незавершённого prefill, выбранных запросов и глобального лимита 40. Дубликаты считаются один раз. Проверка проходит внутри временной блокировки device prefix. |
| 5: park chunked prefill | Чанк сохраняется вместе с его блокировками, если следующая страница не помещается после резерва других запросов. Собственный будущий резерв не блокирует его следующий шаг. Вторая длинная chunked-заявка не может занять его слот. |
| 6: short bypass | До 512 дополнительных page-aligned input-токенов на весь батч. Новый короткий запрос не получает повторно полный лимит. Можно отключить переменной окружения. |
| 7: skip not fitting | Сначала штатная очистка состояния отклонённой заявки, затем переход к следующей и сброс `batch_is_full`. До 32 пропусков за проход; после восьми успешных обгонов новые проходы ждут большую заявку. Уже сформированный батч может добавить ещё несколько обгонов. |

Алгоритм сознательно консервативен: резервирует полный `max_new_tokens`, без
CLIP=4096 и new-token-ratio, плюс страницу на заявку. GPU-префикс уменьшает
потребность, host/L3-префикс пока требует места в GPU и её не уменьшает.
Обычные локальные проверки SGLang также остаются. Резерв — расчёт допуска,
а не выделение памяти на все будущие токены.

## Зафиксированный профиль

| Параметр | Значение |
|---|---|
| GPU / модель | 8 × H200 / PhalaCloud GLM-5.3 W4AFP8, 78 слоёв |
| TP / PP / EP / DP / DCP | 2 / 4 / 1 / 1 / 1; CP выключен |
| Разделение слоёв | 21,20,20,17 — вариант коллеги, оптимальность для W4 не подтверждена |
| KV | FP8 E4M3, page 64 |
| Scheduler | 40 глобально, до 10 на PP микробатч, async depth 0 |
| Prefill | chunk 4096, mixed chunk, штатный DSA `flashmla_kv` |
| Decode | `flashmla_kv`, full CUDA graphs до batch 16 на микробатч |
| Память GPU | `mem-fraction-static=0.90` |
| HiCache L2 | write_back, kernel, page_first; 128 GB на rank, до 1024 GB на 8 ranks |
| HiCache L3 | Опционально, отдельный смонтированный каталог; по умолчанию выключен |
| Context | 98304, покрывает тест ~75k input + 1k output |
| Shared experts | fusion выключена для первого сопоставимого W4AFP8 прогона |
| Speculation / CP / DCP custom / Q8 custom | выключены |

128 GB L2 выбрано с запасом относительно лимита pod 1536 GiB; предложенные
187 GB × 8 оставляют мало пространства для остального процесса. Веса остаются
W4AFP8, а не FP8/NVFP4 из расчётов коллеги. L3 не создаётся на прежнем 20 GiB
compile-cache PVC. HiCache хранит повторно используемый KV и не заменяет
память GPU для одновременно активных запросов.

## Образ и сборка

Workflow `GLM53 PP4 colleague image` выполняет CPU-тесты, сборку и публикацию в
GHCR. Публикуемые теги при успешном запуске:

- `ghcr.io/leoong55/sglang-lasolovev:glm53-pp4-<12 символов SHA>`;
- `ghcr.io/leoong55/sglang-lasolovev:glm53-pp4-colleague-v1`.

Фактический digest находится в summary успешного workflow. Наличие рецепта или
PR не означает, что образ уже опубликован. Пакет GHCR может требовать login,
если его видимость private; при необходимости публикуйте в своём registry.

По умолчанию CI пытается получить публичный образ с тем же upstream-тегом.
Если он недоступен, задайте repository variable `GLM53_PP4_BASE_IMAGE` на
доступный **непатченный** образ этой базы. Инсталлятор сверяет восемь файлов,
включая модель, W4AFP8 и PP scheduler, и откажется от несовместимого образа.
Он не скачивает веса модели и не меняет версии CUDA/torch/sgl-kernel.

Сборка в вашем окружении из корня репозитория (при необходимости подставьте доступное зеркало BASE_IMAGE):

```bash
git fetch origin work/glm53-pp4-colleague
git switch --detach origin/work/glm53-pp4-colleague

docker build \
  -f deploy/glm53-pp4-colleague-v1/Dockerfile \
  --build-arg BASE_IMAGE=lmsysorg/sglang:v0.5.19-latest-0bcd822377da \
  --build-arg SOURCE_COMMIT="$(git rev-parse HEAD)" \
  -t ghcr.io/leoong55/sglang-lasolovev:glm53-pp4-colleague-v1 .

docker push ghcr.io/leoong55/sglang-lasolovev:glm53-pp4-colleague-v1
```

## Запуск

После успешной сборки, на свободном узле с восемью H200:

```bash
docker run -d --name glm53-pp4-colleague \
  --gpus all --ipc=host --network=host \
  --ulimit memlock=-1 --ulimit stack=67108864 \
  -v /path/to/GLM-5.3-W4AFP8:/model:ro \
  ghcr.io/leoong55/sglang-lasolovev:glm53-pp4-colleague-v1
```

`/path/to/GLM-5.3-W4AFP8` должен быть реальным каталогом W4AFP8-весов на Docker-хосте.
Замените этот пример на ваш путь к весам.
Контейнер слушает `:8080`, имя модели в API — `GLM-5.3`.
Для отдельного Kubernetes deployment используйте `manifest.yaml` в этой папке:
в нём нужно подставить свой model PVC вместо `glm53-w4afp8` и при необходимости
imagePullSecrets для приватного registry. Имена deployment/selector/service отдельные.

```bash
kubectl apply -f deploy/glm53-pp4-colleague-v1/manifest.yaml
kubectl logs -f deployment/sglang-glm53-pp4 -c sglang
```

Нужен свободный узел с 8 GPU. Одновременный запуск двух восьмикарточных вариантов
на одном восьмикарточном узле невозможен. Сам PR не применяет manifest к кластеру.

Опции launcher:

```bash
# Печать точных аргументов без запуска модели.
docker run --rm IMAGE --print-command

# L2 выключен для отдельной абляции.
docker run ... IMAGE --hicache-size 0

# L3 на отдельном большом диске: 250 GB на PP stage, до ~1 TB всего.
docker run ... -v /data/glm53-pp4-l3:/cache/l3 IMAGE \
  --l3-path /cache/l3 --l3-max-size 250G
```

В синтаксисе примеров `IMAGE` и `...` — обозначения для вашего образа и общих
Docker-флагов из полной команды выше. Для L3 требуется отдельный каталог,
которым не пользуются другие серверы.

Переменные для абляции:

- `SGLANG_PP_FULL_NEED=0`: штатная политика планировщика при той же TP2/PP4-топологии;
- `SGLANG_PP_SHORT_BYPASS_TOKENS=0`: отключить только short bypass.

## Проверка на H200

Локально проверяются арифметика резервов, лимит 40, prefix lock, сохранение
припаркованного чанка, запрет второго chunked prefill, лимит bypass,
ограничение обгонов, точная установка/повторная установка и отказ на другой базе.
Методы PrefillAdder исполняются с fake pools; полноценного CUDA scheduler в
этих CPU-тестах нет.

На стенде сначала проверить успешную загрузку и полный ответ короткого запроса,
затем несколько длинных запросов на границах PP стадий. Для сравнения точности
нужен последовательный stock TP2/PP4 прогон с теми же весами и prompts.

Целевой прогон: прежние 300 запросов, concurrency 40, ~75k input + 1k output,
20 общих префиксов по ~60k. Отдельно фиксировать холодный/тёплый кэш; не сравнивать
холодный v3 с прогретым HiCache. Записать minimum KV pool по PP stages, фактические
input/output/cache-hit tokens, TTFT/TPOT/ITL p50/p95/p99, throughput, retractions,
ошибки и строки `PP full-need admission: active=40 cap=40`.
Такая строка подтверждает допуск 40 живых запросов в момент формирования батча;
она не доказывает 40 одновременно декодирующих запросов или устойчивость всего
прогона. Нужны временной ряд и серверные метрики, а не только client concurrency.

Это сравнение двух комплексных вариантов. Чтобы отделить пользу патчей от
топологии и HiCache, дополнительно сравните stock PP4 (policy=0), patched PP4 и
patched PP4 без L2, с одинаковыми весами/нагрузкой. Победитель заранее не назначен.
