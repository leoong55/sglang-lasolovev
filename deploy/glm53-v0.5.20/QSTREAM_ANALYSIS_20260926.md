# Q-stream: причинный анализ, 26 сентября 2026

## Что измерено

P4 eager: fresh 128k TTFT 14,150 с. P6 с tile graphs: 11,242 с — снижение примерно на 20,6%. Однако P3 с KV-gather занимает 5,708 с. Графы сокращают регрессию, но новый attention пока нельзя рекомендовать вместо старого.

P6 прошёл 627 нагрузочных запросов без ошибок. Это проверка завершения запросов, не доказательство полной численной корректности модели. Отдельный диагностический запрос 128k/1 output не включён в performance-таблицу. Он записал CPU/CUDA traces на всех восьми ranks; архив и 11 файлов проверены по SHA256.

## Повторный capture: реальная стоимость и ошибочная первая оценка

1104 записи capture в server.log включают запуск и прогрев. В окне performance на каждом rank было 133 capture и примерно 11,4–11,94 с суммарного CPU elapsed. Суммировать это время между ranks нельзя: работа идёт параллельно. Общая сумма 975 с по журналу не является задержкой нагрузочных тестов.

Graph cache хранит один `tile_graph`; ключ включает форму KV view. При изменении округлённой capacity, в том числе её уменьшении, граф пересоздаётся. Возможный адресный фикс — ограниченный набор стабильных capacity/buffers. Но устранение capture само по себе не объясняет весь разрыв с KV-gather.

## Обмены и вычисления

На каждую порцию из 256 локальных Q выполняются четыре collective: gather Q, gather indices, gather LSE, reduce-scatter FP32 output. При 2048 Q/rank это восемь порций на слой. Для 78 слоёв и восьми чанков получается 4992 порции, или 19968 collective-вызовов. Графы сокращают число CPU-запусков, но не устраняют эти обмены.

В диагностическом trace TP0 за два шага prefill:

| Операция | Число kernels | Сумма длительностей |
|---|---:|---:|
| FP32 reduce-scatter | 1250 | 428,54 мс |
| NCCL all-gather, включая другие участки модели | 4102 | 379,78 мс |
| BF16 reduce-scatter | 150 | 258,46 мс |
| Sparse Q8 attention | 1250 | 185,39 мс |

Это суммы длительностей kernels под profiler, не разложение TTFT на независимые части. Операции могут перекрываться; сам profiler влияет на время. Нельзя складывать ranks или CPU/GPU-категории. Также заметны отдельные elementwise where/mul/casts; их соответствие LSE correction нужно уточнять по связям CPU/GPU events.

CPU trace: 1406 `cudaGraphLaunch` занимают суммарно 971,55 мс внутри профилируемых шагов. Частые мелкие graph launches не бесплатны. Это обосновывает проверку более крупных Q-порций, но ещё не доказывает, что такой патч обгонит KV-gather.

## Следующие проверяемые гипотезы

1. Увеличить Q tile и проверить снижение количества collective и graph launches при сохранении numerical parity и запаса памяти.
2. Если trace подтвердит значимую стоимость LSE correction, объединить её elementwise-операции, сохранив FP32 и обработку пустых shards.
3. Устранить ненужный recapture при уменьшении capacity, не захватывая устаревшие адреса и не нарушая одинаковую последовательность collective на ranks.
4. Приоритетно профилировать быстрый KV-gather путь после P6buckets. Цель пользователя — улучшить рабочий клиентский TTFT, а не только сократить регрессию Q-stream. Проверить и накладные расходы самой P0-диагностики.

## Первичные источники

- [NCCL: Using CUDA Graphs](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/cudagraph.html): графы сокращают host launch overhead; capture/replay коллективных операций должны быть согласованы на всех ranks. Новые настройки из документации нельзя переносить без проверки установленной версии NCCL.
- [SGLang CP refactor roadmap #27252](https://github.com/sgl-project/sglang/issues/27252): upstream описывает распределённые между model, indexer и backend преобразования layout. Roadmap полезен для проверки границ реализации, но не доказывает ускорение нашего GLM и не является готовым исправлением.

## Почему MLA меняет оценку выгоды

Trace подтвердил Q `[256,64,576]` на локальную порцию и собранный Q `[1024,64,576]`. Частичный attention output `[1024,64,512]` превращается в FP32 для коррекции/reduce-scatter. За один слой чанка 16k на rank (2048 локальных Q) суммарный вход reduce-scatter составляет **1024 MiB**; локальный вход Q all-gather — **72 MiB**, полный выход — **288 MiB**. Все эти размеры относятся к отдельному rank, не к сумме восьми GPU.

Старый полный packed MLA KV для 128k — **82 MiB** (656 bytes/token, подтверждено dequant_k_cache.py). В действительности старый gather передаёт только prefix: перед последним чанком 112k, то есть **71,75 MiB** полного prefix buffer; новые KV уже доступны через прежний CP-путь. Q-stream добавляет обмен многоголовыми Q/outputs вместо компактного MLA prefix. Именно множитель **64 heads** делает эту замену дорогой.

`qstream-communication-sizing.json` содержит воспроизводимые размеры и отдельную теоретическую ring-оценку. Это не измеренные сетевые байты и не весь трафик модели. Увеличение tile уменьшает число запусков, но не устраняет объём Q/FP32 outputs; fused correction уменьшает локальные memory passes, но тоже не убирает его. Поэтому при 128k не следует обещать, что косметический фикс Q-stream обгонит KV-gather. Требуется либо существенно иное распределение данных, либо более длинный контекст, где баланс объёмов изменится. Для текущей задачи приоритет — оптимизация KV-gather пути по его собственному trace.
