# Адаптация H200.zip для независимого TP/PP эксперимента

Исходный архив: SHA256 `8539bd1c9988a72c8eaf1f596cb97863c8b8ca4052c10dbe321c900f47b9a6f2`.
Код форка наследует v9.14 `219206f7db9f7ffb24dad2605edf72af62d4939e`; профиль запуска строится независимо. Предыдущий вывод «TileLang-патч не нужен из-за нашего FlashMLA/DCP» больше не используется: пользователь выбрал отдельный TileLang TP/PP стенд.

TileLang поддерживает CUDA/Hopper. Ограничение было в конкретном SGLang dispatch, а не в возможности использовать TileLang на H200. Документация проекта: https://github.com/tile-ai/tilelang ; архитектура Hopper: https://docs.nvidia.com/cuda/hopper-tuning-guide/index.html .

## Решения по всем патчам

| № | Архив | Решение в новой ревизии |
|---|---|---|
| 1 | `pp-residual` | Нет целевого `glm5_next.py`; полный GLM использует другую реализацию PP. Не добавлять отсутствующий model class ради применения diff. Проверять фактический PP-контракт полного GLM на GPU. |
| 2 | `kpool-logits-chunk` | Нет `dsa_indexer_kpool.py`; native `dsa_indexer.py` уже вызывает `_should_chunk_mqa_logits` и выполняет logits/topk по чанкам. Сохраняем этот механизм. |
| 3 | `fp8-tilelang` | Адаптирован для CUDA/H200: dispatch, device-aware launch geometry, raw writer/allocator, защита d_tail=0. |
| 4 | `admit-full-need` | Перенесена идея; ledger переписан с дедупликацией всех микробатчей, учётом allocated KV, pending prefill и страниц под временной блокировкой prefix. |
| 5 | `park-chunked-prefill` | Перенесён с сохранением escape для одиночного chunk и проверкой наличия runnable decode. |
| 6 | `short-bypass` | Перенесён с отдельным расходуемым бюджетом на батч; обе native ветки admission. |
| 7 | `skip-not-fitting` | Перенесён с очисткой batch_is_full после отказа, сохранением cleanup и различением локального отказа / общего исчерпания. |

Это пять адаптированных патчей и две адресные правки к отсутствующим реализациям. Формулировка «все семь применены» была бы неверной. Причины 1/2 не связаны с предыдущей топологией или её совместимостью.

## TileLang FP8: что изменено

`overrides.py` разрешает CUDA FP8 при TileLang в обеих фазах. Смешение TileLang raw KV с backend другого layout отклоняется: reader и writer одного KV-пула должны одинаково понимать байты.

`tilelang_kernel.py` отправляет CUDA FP8 в существующее `sparse_mla_fwd_decode_partial_fp8` + combine. Консервативные block_I64/threads256/block_per_SM1 сохранены как отправная точка; число SM читается через `torch.cuda.get_device_properties(q.device).multi_processor_count`, а не зашивается как188 для RTX. Код d_tail0 ограждён при построении ядра. Подбор оптимального tile для H200 ещё не выполнен.

`kv_cache_configurator.py` возвращает raw `kv_lora_rank + qk_rope_head_dim` для TileLang в обеих фазах. `memory_pool.py` выбирает FP8 raw writer по фактической размерности пула. Архивная безусловная замена всех CUDA DSA writers не используется. Для 512+64 это576 байт MLA KV на токен/слой; индексный cache и остальные буферы считаются отдельно.

FP8-ядро также квантует Q и промежуточные softmax probabilities. Корректный размер пула не доказывает качество результатов. `check_tilelang_gpu.py` проверяет writer, numerical reference и graph replay на целевой карте. В этом окружении H200 нет, поэтому такой результат пока отсутствует. Модельная проверка качества и полноценный PP inference остаются отдельными обязательными шагами стенда.

Не применённые в архиве `v1_tile`/`v1_headblock` относятся к другому BF16 v1 kernel и shared-memory ограничениям SM120. В выбранном FP8 partial+combine пути они не выполняются; переносить эти числа в H200-профиль нет основания.

## Полное резервирование

Архив правильно выявил долг всех PP-микробатчей. Исходная формула могла повторно посчитать запрос из inflight и can_run_list, не учитывала незаконченный prefill для inflight, страницы и изменение evictable после lock; исключения в `_lp` скрывались возвратом0.

Адаптация объединяет inflight, running, chunked, can_run_list и кандидата по идентичности объекта. Завершённые запросы исключаются. Целевой endpoint — длина входа + max_new_tokens. Уже выделенные KV и защищённый prefix вычитаются; ещё не выделенный prefill из can_run_list остаётся долгом. Резерв округляется до страницы и включает запас страницы allocator. Кандидат проверяется при заблокированном prefix; на ignore_eos/disabled-tree пути блокируемого radix-prefix нет. Нет broad exception с возвратом0.

Это консервативное admission, не гарантия отсутствия OOM при любой комбинации возможностей движка. Нужны PP complete/abort/retraction циклы на реальном allocator. Область эксперимента — native полный GLM MLA без speculative/disaggregated/hybrid-state serving.

## Short-bypass и skip

В исходнике при S512 и остатке чанка−448 следующий короткий запрос512 проходил, получалось−960. Порог отдельного запроса не ограничивал суммарный дополнительный бюджет.

Теперь у каждого PrefillAdder есть `rem_short_bypass`. Только дополнительные page-aligned токены сверх оставшегося обычного chunk-бюджета расходуют этот остаток. После448 дополнительных токенов можно добавить64, но нельзя512 или65. Обычный и ignore_eos/disabled-radix пути используют одну проверку. Лимит input/KV не отменяется.

Отказ из-за короткого бюджета обозначается отдельным `SKIP`; с включённым skip можно рассмотреть меньшего кандидата дальше в очереди. `OTHER` от delay/dllm/прочих ограничений не обходится. Сброс `batch_is_full` выполняется после native cleanup; общее исчерпание ресурсов останавливает сканирование.

## Что доказывают проверки

CPU тесты выполняют реальные scheduler-методы с фальшивыми границами allocator/worker, проверяют все микробатчи, дедупликацию, unfinished prefill, page slack, два пути short admission, skip cleanup, профили и инварианты A/B. Отдельно проверяются CUDA dispatch и gate. Это не выполнение CUDA и не модельная численная валидация.

Одинаковый TileLang/FP8 стек в A/B исключает подмену эффекта топологии эффектом backend. Добавлен PP2, чтобы вывод не зависел только от одной глубины конвейера. Архивная PP4 раскладка — кандидат, а не доказанный optimum. Измерять throughput и ms/token при одинаковом resident C, сохраняя также точки отказа по capacity/stability. Не гарантировать заранее нужный знак результата.
